# 운영 RUNBOOK — 장애 대응과 롤백

이 문서는 **당직자가 새벽에 읽는 것**을 전제로 쓴다. 배경 설명은 링크로 넘기고
여기에는 판단과 명령만 둔다.

문서의 규율은 저장소 전체와 같다: **여기 적힌 것은 저장소에서 확인 가능한
것뿐이다.** 확인되지 않은 절차는 "미확정"으로 표시하고 추측으로 채우지 않는다.
당직 중에 추측한 절차를 따르는 것이 절차가 없는 것보다 위험하다.

---

## 0. 30초 판단

| 증상 | 먼저 볼 것 | 절 |
|---|---|---|
| 전면 장애 (모든 요청 5xx) | `/api/health` | §2 |
| 페이지는 뜨는데 화면이 깨짐·버튼 무반응 | 브라우저 콘솔의 청크 404 | §5 |
| 특정 기능만 실패 | 해당 라우트의 `event: "request"` 로그 | §3 |
| 도면 분석만 실패 | `/api/drawing-jobs` 503 여부 | §6 |
| 결제·인증 이상 | 외부 공급자 상태 먼저 | §7 |

**롤백을 먼저 할지 원인부터 볼지**: 사용자 영향이 있으면 롤백이 먼저다(§4).
원인 규명은 롤백 후에 한다. 예외는 데이터가 이미 잘못 쓰이고 있는 경우로,
그때는 쓰기를 먼저 멈춘다.

## 1. 상태 확인

```bash
curl -sS https://<host>/api/health | jq
```

응답 계약([route.ts](../src/app/api/health/route.ts)):

- **200 `healthy`** — 정상
- **200 `degraded`** — 일부 의존성이 미설정이거나 느림. 서비스는 동작한다.
- **503** — critical 의존성 down. 사용자 영향 있음.

의존성별 의미:

| 의존성 | `degraded` | `down` |
|---|---|---|
| Supabase | 미설정(`Not configured`) | 연결 실패 — 저장·조회 전반 영향 |
| Weaviate | 미설정 — 로컬 폴백 동작 중 | 연결 실패 — 검색 품질 저하 |

상세 필드는 인증이 있어야 보인다(`canViewDetails`). 토큰 없이 나오는 것은 요약뿐이다.

## 2. 전면 장애

1. `/api/health` 가 **503** → 의존성 문제다. §7 로.
2. `/api/health` 가 **응답 없음** → 프로세스가 죽었거나 뜨지 못했다.
   - 컨테이너 로그에서 부팅 실패를 확인한다. 가장 흔한 원인은 필수 환경변수 누락이다.
   - 필수 키(`src/lib/env.ts` 의 `required: true`):
     `NEXT_PUBLIC_FIREBASE_API_KEY` · `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN` ·
     `NEXT_PUBLIC_FIREBASE_PROJECT_ID` · `NEXT_PUBLIC_FIREBASE_APP_ID` ·
     `NEXT_PUBLIC_SUPABASE_URL` · `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - 부팅 시 `validateEnv()` 가 **누락 키의 이름만** 로그에 남긴다. 값은 남기지 않는다.
3. 원인이 30분 안에 안 잡히면 롤백한다(§4). 진단은 롤백 후에 계속한다.

## 3. 특정 라우트만 실패

모든 API 라우트가 구조화 로그를 남긴다(2026-07-25 배선, 49/49):

```
{"level":"error","event":"request","route":"/api/xxx","status":500,"durationMs":123,"requestId":"..."}
```

- `requestId` 는 프록시가 발급하고 응답 헤더 `x-esa-request-id` 로도 나간다.
  사용자 제보에 이 값이 있으면 로그를 바로 찾을 수 있다.
- 로그의 비밀값은 마스킹된다(`[REDACTED]`). SHA-256 영수증 해시는 **일부러 남긴다** —
  마스킹된 걸로 착각하지 말 것.
- `level` 은 응답 status 에서 파생된다: 5xx=error · 4xx=warn · 그 외 info.

로그가 **아예 없으면** 요청이 라우트에 도달하지 못한 것이다 — 프록시(`src/proxy.ts`)의
레이트리밋·CORS 차단이나 그 앞단을 본다.

## 4. 롤백

**미확정 — 이 저장소에는 배포 파이프라인이 정의돼 있지 않다.**
`Dockerfile` · `docker-compose.yml` · `vercel.json` 이 있으나, 운영 호스트가 어느
것으로 어떻게 배포되는지는 저장소에서 확인되지 않는다. 아래는 산출물 기준의
일반 절차이며, **실제 운영 경로를 확인한 사람이 이 절을 확정해야 한다.**

원칙만 확정적으로 적는다:

1. **직전 정상 리비전으로 되돌린다.** 앞으로 고치지 말고 뒤로 돌린다.
   마지막 CI green 커밋을 기준으로 삼는다 — `main` 의 CI 는 docs·tsc·lint·test·
   빌드·`gate:chat-live`·`gate:pdf`·Playwright 를 모두 통과해야 green 이다.
2. **DB 마이그레이션이 포함된 배포는 코드만 되돌려도 복구되지 않는다.**
   `supabase/migrations/` 에 새 파일이 있었는지 먼저 확인한다.

   현재 상태(실측 2026-07-29 · 9 개 파일): 테이블 생성 30 · 컬럼 추가 27 ·
   `DROP TABLE` 0 · `DROP COLUMN` 0. 즉 **더하기만 하므로 구버전 코드가 새
   스키마 위에서도 돌아간다** — 003 이후로 되돌리는 것은 코드만으로 안전하다.
   (앞서 이 자리에 "전부 정책·제약 변경"이라고 적혀 있었으나 사실이 아니었다.
   결론은 같지만 이유가 달라서, 파괴적 문장이 하나 들어오는 순간 안내가 조용히
   틀리게 된다. 그래서 조건 자체를 검사로 잠갔다 —
   `src/lib/__tests__/migration-additive-contract.test.ts`.)

   **예외 — 002 이전으로는 되돌리지 말 것.** `002_firebase_contract.sql` 이
   `calculation_receipts` 의 컬럼 두 개를 개명한다
   (`calc_id → calculator_id`, `result → outputs`). 하위호환 창이 없어서
   001 시절 코드는 이 스키마에서 동작하지 않는다. 002 이전이 필요하면
   코드 롤백이 아니라 **데이터 복원 절차**로 간다.
3. **롤백 후 `/api/health` 와 사용자 경로 1개를 직접 확인**하고 나서 정상 선언한다.
   "배포가 끝났다"는 정상의 증거가 아니다.

## 5. 화면이 깨진다 (청크 404)

증상: 페이지 HTML 은 오지만 스타일이 없거나 상호작용이 죽어 있다. 브라우저
네트워크 탭에 `/_next/static/...` 404 가 보인다.

원인은 거의 항상 **standalone 산출물에 정적 자산이 없는 것**이다.
`output: 'standalone'` 은 `.next/static` 과 `public` 을 복사하지 않는다.

- 2026-07-25 부터 `postbuild` 가 자동 복사한다(`scripts/copy-standalone-assets.mjs`).
  빌드 로그에 `copy-standalone-assets: 완료` 가 있어야 한다.
- 그 줄이 없다면 빌드가 `postbuild` 를 건너뛴 것이다(예: `next build` 직접 호출).
- Docker 는 `Dockerfile` 이 COPY 로도 채운다(36~39행).

**오진 주의**: 서비스워커·빌드ID·브라우저 캐시를 의심하기 쉽지만, 네트워크 탭의
청크 404 가 보이면 그게 답이다.

## 6. 도면 분석만 실패

`지속형 작업 저장소가 설정되지 않아 도면 분석 작업을 시작할 수 없습니다.` (503)

- 출처: `src/app/api/drawing-jobs/route.ts`. `isDrawingJobStoreAvailable()` 이 false 다.
- 내구 저장 경로도 임시 저장 허용도 없을 때 발생한다. **의도된 fail-closed** 이며,
  저장에 실패했는데 성공한 척하지 않기 위한 설계다.
- 조치: 배포 환경의 내구 저장 설정을 확인한다. 이 상태에서도 **단일 페이지
  DXF/PDF 벡터 파싱은 동작해야 한다** — 안 된다면 그건 별개 결함이다.

### 다중 페이지 PDF 에서 2페이지부터 기기가 0개다

- 증상: 예외도 경고도 없이 `components: []`. "이 장에는 기기가 없다"와 구분되지 않는다.
- 원인(2026-08-05 수리): pdf.js 가 받은 `ArrayBuffer` 를 워커로 transfer 해 **detach**
  시킨다. 파서가 사본이 아닌 뷰를 넘기면 첫 페이지 이후 호출자의 버퍼가 비어 있다.
- 확인: 파싱 전후로 `buffer.byteLength` 를 찍어 0 이 되는지 본다.
- 회귀 시험: `src/engine/topology/__tests__/pdf-vector-parser-buffer-ownership.test.ts`.

### 1페이지가 아닌 페이지에서만 구획이 `failed` 다

- 증상: 구획 role call 오류가 `rescanTargets[N] 값이 현재 도면 범위를 벗어났습니다`.
- 원인(2026-08-05 수리): 팀에 넘기는 스냅샷은 항상 `page = 1` 인데(페이지 한 장을
  래스터로 넘기므로 그 좌표계에선 맞다) 오케스트레이터가 **문서 페이지 번호**를
  넣었다. 좌표가 아니라 페이지 번호 불일치다.
- 여파: 수리 전에는 **1페이지가 아닌 모든 페이지에서 재스캔 복구가 통째로 죽어 있었다.**
  단일 페이지 업로드로만 시험하면 우연히 일치해 드러나지 않는다.
- 회귀 시험: `document-orchestrator.test.ts` 의 `pageIndex: 4` 픽스처.

## 7. 외부 의존성

| 의존성 | 없을 때 동작 | 확인 |
|---|---|---|
| Supabase | 저장·조회 실패. health `down` | health 의 Supabase 항목 |
| Weaviate | 로컬 폴백으로 검색 계속. health `degraded` | health 의 Weaviate 항목 |
| Firebase | 인증 실패 → 보호 API 401 | 필수 env 4종 |
| Stripe | 결제 경로만 영향 | 서명 웹훅 원장 |
| AI 공급자(BYOK) | 사용자 키 문제는 사용자별 장애다 | 해당 라우트의 request 로그 |

**BYOK 키는 사용자 브라우저에 암호화 저장된다.** 서버에 없으므로 서버 쪽에서
"사용자 키를 확인"하는 절차는 존재하지 않는다.

## 8. 사후

1. 타임라인을 남긴다 — 최초 증상, 인지 시각, 조치, 복구 확인 시각.
2. **재발 방지를 게이트로 만든다.** 문서에 "주의"를 적는 것은 방지가 아니다.
   이 저장소의 규율은 등록이 아니라 발화다 — 테스트나 CI 단계로 옮겨야 유효하다.
3. 장애가 게이트의 공백을 드러냈으면 그 공백을 `docs/DORMANT_MANIFEST.md` 나
   `SECURITY.md` 「알려진 공백」에 사유와 함께 등재한다.

## 9. 이 문서의 공백

정직하게 적어 둔다. 채우려면 운영 환경 접근이 필요하다.

- **배포·롤백 실제 명령**(§4) — 운영 호스트와 파이프라인 미확인.
- **on-call 로테이션·에스컬레이션 연락처** — 저장소 밖 정보.
- **SLO 와 경보 임계** — 정의된 것이 없다. 경보가 없으면 이 문서는 사용자 제보가
  있어야만 펼쳐진다.
- **부하 한계** — Stress/Load 실측이 없어 "몇 명까지 버티는가"에 답할 수 없다.
