# 일반 AI 판단 책임 계약 수리 설계

**기준일:** 2026-08-09

**대상 기준선:** `1dd48e905be6fb9ec179f6a48417f8f3b4b5951d`

**범위:** `/api/chat`의 일반 자유문답 출력 후처리
**제외:** 도면 V3 결정론적 제안, 모델 파인튜닝, 신규 공급자, UI 재설계

## 1. 문제와 성공 조건

현재 시스템 프롬프트는 AI가 가능한 판단을 먼저 내리고 사용자에게 역질문하지 않도록 지시한다. 그러나 `/api/chat` 출력 필터는 무출처 수치·가짜 계산기 출처·기준서 인용만 검사하므로, 모델이 다음과 같이 답해도 그대로 통과한다.

- “몇 개인지 사용자가 판단해 주세요.”
- “어느 쪽이 맞는지 선택해 주세요.”
- “필요한 값을 알려 주시면 판단하겠습니다.”

성공 조건은 다음과 같다.

1. 정상 답변은 추가 모델 호출이나 문장 변경 없이 통과한다.
2. 판단 책임 전가가 검출된 답변만 같은 공급자·모델로 최대 한 번 교정한다.
3. 교정 답변은 `ESA 잠정 판단 → 근거 → 결론 변경 조건`을 포함하고 질문형 인계를 만들지 않는다.
4. 교정 결과도 계약을 어기면 원답을 노출하지 않고 결정론적 `판단 미완결` 응답으로 닫는다.
5. 기존 수치·출처 필터는 교정 뒤에도 반드시 다시 실행한다.
6. 서버 키를 쓰는 교정 호출은 별도 토큰 예산을 예약·정산하며, 예산이 없으면 호출하지 않고 결정론적 폴백을 사용한다.

## 2. 검토한 접근

### A. 질문 문장 삭제

비용은 없지만 문맥이 끊기고, 모델이 판단 자체를 하지 않은 답변에서 질문만 지우면 빈 답이 된다. 채택하지 않는다.

### B. 모든 답변을 구조화 JSON으로 생성

계약은 강해지지만 설명형 질문·간단한 용어 질문까지 경직되고 모든 공급자 계약을 바꿔야 한다. 현재 결함 반경보다 크므로 채택하지 않는다.

### C. 위반 답변만 1회 교정 후 실패 폐쇄

정상 응답 비용은 그대로이고, 위반 응답만 판단형 문장으로 다시 생성할 수 있다. 재실패를 결정론적으로 차단할 수 있어 이 방식을 채택한다.

## 3. 구성요소

### 3.1 `chat-decision-contract.ts`

순수 함수만 두어 공급자 호출과 분리한다.

- `inspectDecisionContract(text, language)`
  - 책임 전가 표현과 답변 말미의 입력 요구 질문을 검출한다.
  - 모든 물음표를 금지하지 않는다. 인용문·수사 질문·사용자 질문 재진술은 위반으로 잡지 않는다.
  - 한국어와 현재 라우트가 지원하는 영어만 검사한다.
- `buildDecisionRepairInstruction(query, answer, language)`
  - 기존 답변의 근거와 출처 태그를 보존한다.
  - 새 수치·조항을 만들지 않는다.
  - 판단 불가능 자체도 ESA의 판단으로 명시하고 해당 축만 보류한다.
  - 결론을 바꿀 최소 정보는 질문이 아닌 선언형 목록으로 쓴다.
- `buildDecisionContractFallback(language)`
  - 원답을 노출하지 않는다.
  - “현재 응답은 판단 미완결”, “해당 판단축만 보류”, “나머지 분석은 유지”를 명시한다.

검출 대상은 사용자가 답을 대신 만들게 하는 표현으로 제한한다. “현행 원문과 대조하십시오”, “무전압 확인 후 작업하십시오”처럼 안전을 위한 행동 지시는 책임 전가로 보지 않는다.

### 3.2 채팅 생성 함수 분리

현재 `buildStreamingResponse` 안의 공급자별 생성 코드를 `generateChatText`로 분리한다. 반환값은 본문, 종료 사유, 실제 토큰 수다. 첫 생성과 교정 생성은 같은 함수를 사용해 공급자별 동작이 갈라지지 않게 한다.

교정 호출은 다음 제한을 갖는다.

- 동일 공급자·동일 모델
- 최대 1회
- 출력 상한 `min(기존 maxTokens, 2048)`
- 원래 대화 전체 대신 마지막 사용자 질문, 원답, 교정 계약만 전달
- 도구 사용 없음
- 요청 취소 신호와 기존 공급자 제한시간 승계

### 3.3 토큰 예산

BYOK·로컬 계정·온프레미스는 기존 정책대로 서버 예산을 쓰지 않는다. 서버 키는 위반이 실제 검출된 시점에만 교정 프롬프트 추정 토큰과 출력 상한을 추가 예약한다.

- 예약 성공: 교정 호출 후 실제 사용량으로 별도 정산
- 예약 실패: 교정 호출 없이 결정론적 폴백
- 최초 호출 예약과 교정 호출 예약을 합쳐 한 번 정산하지 않는다. 각각 독립 영수증으로 다룬다.

## 4. 처리 순서

```text
사용자 질문
  → 기존 시스템 프롬프트와 계산기 영수증
  → 1차 모델 생성
  → 판단 책임 계약 검사
      ├─ 통과: 기존 수치·출처 필터
      └─ 위반: 교정 예산 확인 → 같은 모델 1회 교정
                 → 판단 책임 계약 재검사
                    ├─ 통과: 기존 수치·출처 필터
                    └─ 실패/예산 없음/호출 실패: 결정론적 판단 미완결 응답
  → 전체 답변을 모은 뒤 SSE 전송
```

모델 토큰은 현재처럼 전체 검증이 끝나기 전 클라이언트로 보내지 않는다.

## 5. 관측과 오류 처리

`chat_generation_complete` 로그에 다음 비민감 필드를 추가한다.

- `decisionContractPassed`
- `decisionRepairAttempted`
- `decisionRepairSucceeded`
- `decisionViolationCount`

원답·교정답·사용자 질문은 새 로그에 넣지 않는다. 교정 호출 실패는 일반 채팅 전체를 500으로 만들지 않고 결정론적 폴백으로 닫는다. 요청 취소는 추가 호출을 시작하지 않는다.

SSE의 `filter` 메타데이터에는 `decisionContract` 상태를 추가하되, 기존 클라이언트가 모르는 필드를 무시할 수 있으므로 계약을 깨지 않는다.

## 6. 테스트 계약

### 순수 함수

- “사용자가 판단해 주세요”, “몇 개인지 알려 주세요”, “어느 쪽인지 선택해 주세요” 검출
- 잠정 판단과 선언형 결론 변경 조건은 통과
- 안전 지시·원문 대조·인용된 사용자 질문은 오탐하지 않음
- 영어의 직접 책임 전가 검출
- 교정 지침에 새 수치·질문형 인계 금지 계약 포함

### 라우트

- 정상 답변은 공급자 1회 호출
- 위반 답변은 최대 2회 호출하고 교정 답변만 전송
- 2차 답변도 위반이면 원답을 숨기고 폴백 전송
- 교정 실패·예산 거절도 폴백 전송
- 교정 답변의 무출처 수치는 기존 출력 필터가 차단
- 실제 토큰 예약·정산이 1차와 교정 호출에서 분리됨

## 7. 비목표와 잔여 한계

- 모델이 내린 기술 판단의 진실성을 이 계약만으로 보증하지 않는다. 근거·계산·규정 검증은 기존 계층이 담당한다.
- 단순한 물음표 존재만으로 답을 차단하지 않는다.
- 사용자가 명시적으로 인터뷰·퀴즈·문진을 요청한 대화 모드는 이번 범위에 넣지 않는다.
- 공급자 장애를 다른 공급자로 자동 폴백하지 않는다.

## 8. 수용 기준

관련 회귀 테스트, 전체 Jest, TypeScript, ESLint, production build가 통과하고 다음 정적 반증이 성립해야 한다.

- `/api/chat`에서 계약 검사 함수 production caller가 존재한다.
- 교정 호출 상한은 코드상 1회다.
- 수치·출처 필터는 최종 선택된 답변 뒤에 실행된다.
- 원답은 계약 위반 상태에서 SSE 텍스트로 전송되지 않는다.
- 로그와 커밋에 API 키·사용자 질문·원답이 포함되지 않는다.
