중급 결선도는 Gemini가 기호 34개와 선 33개를 읽었지만 단일 선분의 양끝이 직접 기기에 닿을 때만 관계를 만들던 조립기 때문에 관계가 5개에 그쳤다. 구획 사이의 수직 분기선을 버스 선망까지 추적하고 평행선은 제외하도록 수리한 뒤 표적 재실행은 관계 20개, 관계 기준 100%, 종합 78%, 247초, 실제 시작 호출 41회였다. 수리 전 51%·관계 33% 대비 개선됐지만 기호축은 퓨즈 14/15, breaker 오탐 5, switch 2/1로 69%여서 전체 80%에는 미달했다.

이번 조사에서 새로 확정·수리한 앱 결함은 12건이다.

1. 비치명 source 실패 하나가 coverage audit 전체를 실패시킴.
2. 실패 뒤 성공한 재시도도 최종 FAIL로 계산함.
3. full-page source 실패를 모든 정밀 구획 재호출로 확대함.
4. 실제 source 실패와 합성 `role` 실패를 중복 재시도함.
5. 3역할 합산 rescan target을 역할별 상한 16개로 잘못 제한함.
6. 완결된 래스터 페이지도 `drawingKind=unknown`만으로 page-survey HOLD 처리함.
7. 서로 다른 source snapshot의 모델 결과를 같은 표로 직접 비교함.
8. 시작하지 않은 예약 호출까지 사용 호출 수로 집계함.
9. graph conflict 원인을 일반 coverage 문구로 소실함.
10. `disconnector`·`isolator`를 switch 평가 축에서 누락함.

### 13차 재스캔 폴백 — 편차 출처 정정과 실측 (2026-08-04)

12차의 편차 진단을 코드로 되짚어 **앞선 "재스캔이 편차를 증폭한다"는 판단이

`failed`이고 `HOLD_RESCAN_UNRESOLVED`가 남았는데도 재스캔을 한 번도 못 돌았다.

원인은 `canRescan`의 `targets.length > 0` 조건이다. 재검사 대상은 감사기의
`rescanTargets`와 `failedRoleRescanTargets`(**역할 호출 실패**)에서만 나온다.
구획 자체가 실패했는데 역할 실패 목록이 비면 대상이 0이 되어, 어디를 다시
볼지 알면서도 포기한다. **재스캔은 편차를 키우는 게 아니라 줄인다.**

수리: 두 경로가 모두 대상을 내지 않고 구획이 남으면 미완료 구획 경계를 대상으로
삼는 결정론적 폴백(`gapRegionRescanTargets`)을 넣었다. 단, **판독 역할 호출이
실제로 실패한 구획만** 고른다 — 그래프 충돌·감사 미해결로 미완료인 구획은 같은
입력을 다시 보내도 같은 결과라 호출 예산만 3배로 태운다. 기존 테스트가 그
부정 케이스(충돌만 있을 때 재시도 없음)를 이미 잠그고 있다.

같은 서버·같은 스냅샷 `--repeat=3` 실측:

|---|---|---|

| 최저점 | 80% | **83%** |

줄었지만 **개선으로 확정하지 않는다** — 두 묶음 모두 3회이고 구간이 겹친다.
확정적으로 말할 수 있는 것은 ① 폴백이 의도한 조건에서 발동했고 ② 3회차는
폴백 조건(역할 호출 실패)을 만족하지 않아 34호출로 남았다는 사실뿐이다.

대가는 시간이다. 재스캔이 도는 회차는 약 400초로 이전의 2배이며, 문서 기한
570초에 더 가까워졌다. 고밀도 도면에서는 이 폴백이 마감 초과를 유발할 수
있으므로, 폴백 대상 상한(`MAX_GAP_FALLBACK_TARGETS = 6`)과 기존 시간 여유

따라서 병합·강등 수리(부분 판독 병합 + 비대칭 규칙)는 각자의 기제를 닫았고,

없으며, 다음 후보는 ① 고아 조각(주변 동형 기기 대비 조각 크기 노드)을

## 14차 접지 소견 세분화 — 그리고 교보재 공백 실측 (2026-08-04)

source·protection·load·bus 로 분류되는 심볼은 갇혀 있어도 강등하지 않는다 — 그 분류가

> 이었다. `sliverRatio` 가 종류별 중앙값 하나를 쓰는 바람에 이봉분포(피더 표
> MCCB vs VCB·ACB draw-out)의 작은 쪽을 통째로 조각으로 오탐했다. 군집 분리로
> 고친 뒤 같은 데이터에서 두 팔의 구간이 겹친다. 이 절의 근거 중 살아 남는 것은
> ③ `unmergedPairRatio` 다. 자세한 것은 21차.

**① 18차 A/B 를 다시 읽으면**(같은 데이터, 다른 자):

| | 라벨 점수 | 고급 조각비 |
|---|---|---|
| 지정문자 無 | 85~87% | **0.041 ~ 0.057** |
| 지정문자 有 | 85~100% | **0.115 ~ 0.149** |
| 판정 | 구간 겹침 → **불가** | 구간 안 겹침 → **갈림** |

조각 절대수도 4/5/6 → 10/14/15 다. 확정 심볼 수는 94~105 대 87~106 으로 비슷한데
조각만 3배다. **원인은 아직 모른다** — 고급에는 지정문자 라벨이 0개라 그 분기는
발화할 수 없다(18차). 자가 조사 대상을 하나 새로 꺼내 놓은 것이고, 그게 자의 일이다.

**② 갇힌 표기 강등(13차)의 효과가 이제 보인다**: 조각비 이상치 꼬리가 사라졌다.
적용 전 중급 20회는 0.043~0.500(이상치 0.14·0.17·0.50), 적용 후 8회는 0.048~0.063
으로 **폭 0.015**. 라벨 점수로는 안 보이던 변화다.

**③ 명판 병합(17차)은 설계대로 작동했다 — 그런데 그게 요점이 아니었다**:
고급 미병합비가 0.014~0.159 에서 **0~0.009** 로 떨어졌다. 접으라고 만든 것을 다
접었다. 그런데 정확도는 안 올랐다. 즉 **남아 있던 미병합쌍의 상당수가 진짜 별개
기기였다**. 17차의 기각 사유("라벨+크기로는 못 가른다")를 지표가 독립적으로 뒷받침한다.

### 한계 — 이 자가 증명하지 않는 것

정답을 안 쓰므로 **"정확하다"를 증명하지 않는다.** 조립기가 자기 입력을 얼마나
정리했는지만 잰다. 세 비율을 다 0 으로 만드는 가장 쉬운 방법은 아무것도 확정하지
않는 것이다 — 그래서 라벨 점수를 대체하지 않고 **함께** 읽어야 한다. 정답이 있는
교보재에서는 라벨 점수가 여전히 정본이고, 이 자는 그 점수가 잡음에 묻히는 구간
(고급 티어·조립기 변경)에서 쓴다.

## 20차 벡터 파싱 실측 — 그리고 조용한 실패 하나 (2026-08-05)

### 그런데 고급 교보재가 애초에 벡터 PDF 였다

`kimm-20210602-design.pdf` p5 — 세션 내내 래스터로 바꿔 VLM 에 먹이던 그 페이지 —

```bash

```

같은 페이지를 `parsePdfToSLD` 로 읽으면:

| | 벡터 경로 | VLM 경로(19차까지) |
|---|---|---|
| 시간 | **805ms** | 250~572초 |
| 결정성 | 같은 입력 → 같은 출력 | 변압기 3/9/7 로 흔들림 |
| 변압기 | 8개, 라벨 정확 (`MOLD TR-1/2/3` · `TR FL&FAN` · `DOWN TR`) | 3~9개 |

라벨을 **원문 그대로** 읽는다. 세 MOLD 변압기가 `@22,31` `@42,31` `@62,31` 로

> VLM 축과 다르므로 이 표는 **속도·결정성·라벨 충실도** 비교로만 읽을 것.
> 벡터 경로의 정확도 채점은 별도 실증이 필요하다(미실시).

### 발견한 결함 — 두 번째 파싱이 조용히 빈 결과를 낸다

`pdf.js` 는 받은 `ArrayBuffer` 를 워커로 transfer 해 **detach** 시킨다. 파서는
`new Uint8Array(pdfBytes)` 를 넘겼는데 이것은 사본이 아니라 **뷰**다. 그래서:

```
호출 전 byteLength: 29345818
1회차 기기: 236   경고: undefined
호출 후 byteLength: 0        ← 호출자의 버퍼가 detach 됐다
2회차 기기: 0     경고: undefined   ← 예외도 경고도 없다
```

**"이 장에는 기기가 없다"와 구분되지 않는다.** 83페이지 설계세트를 페이지별로
파싱하면 1페이지만 살고 나머지는 조용히 빈 결과가 된다.

방어가 호출부에 흩어져 있었다: `sld-team.ts` 는 사본을 떴고(주석까지 있다),
`layout-team.ts` 는 안 떴다. 계약을 지키는 자리를 **파서 안으로** 옮겼다.

시험은 `pdf-vector-parser-buffer-ownership.test.ts` 다. 처음 쓴 판은 수리
없이도 통과했다 — 모의가 실제 pdf.js 처럼 detach 하지 않았기 때문이다. 모의가
`structuredClone(buf, {transfer:[buf]})` 로 실제 detach 하도록 고친 뒤에야
수리 유무를 가른다(수리 있음 2 pass / 없음 2 fail 확인).

`sld-team-independent-review.test.ts` 의 같은 이름 시험은 계약이 옮겨간 자리에
맞춰 고쳤다 — detach 하는 파서 모의는 이제 거짓 전제다. 보장 자체는 위 파서
시험이 **실제 파서로** 지키므로 약화가 아니다.

적었다. **원장 앵커를 확인하지 않고 쓴 것이고, 둘 다 사실이 아니다.**
(CLAUDE.md: "실증이 없다/필요하다"는 판단은 앵커를 확인·재실행한 뒤에만 한다.)

### 실패 구획 3개의 원인은 하나였다 — 수리함

```
p4-full  symbols:      rescanTargets[1] 값이 현재 도면 범위를 벗어났습니다.
p4-r8    symbols:      rescanTargets[1] 값이 현재 도면 범위를 벗어났습니다.
p4-r9    symbols:      rescanTargets[1] 값이 현재 도면 범위를 벗어났습니다.
```

`requestedRescanTargets` 가 `map` 안에서 throw 했다. **대상 하나가 범위를
벗어나면 역할 호출 전체가 실패**하고 같이 온 멀쩡한 대상까지 사라진다. 그
결과 구획이 통째로 `failed` 가 됐다.

수리: 유효한 대상은 살리고 거부한 것은 **사유와 함께 HOLD 로 남긴다**(조용히
버리지 않는다). 전부 잘못됐으면 종전대로 거부한다 — 하나만 나쁜 것과 통째로
쓰레기인 것은 다른 사건이다.

**아직 안 밝힌 것**: 왜 범위를 벗어난 대상이 만들어졌는가. 이 값은 모델 출력이
아니라 **우리가 `params.rescanTargets` 로 넣어준 것**이다. 좌표계 불일치가
유력하지만(재스캔 대상 bounds 와 페이지 스냅샷의 배율) 증거가 없어 단정하지
않는다. 위 수리는 원인과 무관하게 옳다 — 한 개의 실패가 전체를 죽이면 안 된다.

## 21차 남은 3건 추적·조사·수리 (2026-08-05)

20차 말미에 이름 붙여 둔 3건을 끝까지 따라갔다.

### ① 범위 밖 재검사 대상 — 원인 규명·수리 완료

20차에서 "좌표계 불일치가 유력하지만 증거가 없어 단정하지 않는다"고 남긴 건이다.
**좌표가 아니라 페이지 번호였다.**

- `createDrawingSnapshot(buffer, mimeType, prepared.profile)` 는 페이지 인자 없이
  불려 **항상 `page = 1`** 이다(팀에는 페이지 한 장을 래스터로 넘기므로 그 좌표계
  안에서는 맞다).
- 그런데 오케스트레이터의 두 생산자(`failedRoleRescanTargets`,
  `gapRegionRescanTargets`)는 **문서 페이지 번호**(`page.pageIndex + 1`)를 넣었다.
- sld-team 검증의 `bounds.page !== snapshot.page` 가 이를 "현재 도면 범위를
  벗어났습니다"로 거부한다.

**즉 1페이지가 아닌 모든 페이지에서 오케스트레이터가 만든 재스캔 대상이 전부
거부되고 있었다.** 재스캔 복구가 통째로 죽어 있었다는 뜻이다. 이번 세션의 다른
측정은 전부 단일 페이지 업로드(pageIndex 0 → page 1)라 우연히 일치해 안 드러났고,
KIMM 83p 설계세트의 p5 를 PDF 로 직접 넣었을 때 구획 17개 중 3개 실패로 나타났다.

수리: 두 생산자가 `TEAM_SNAPSHOT_PAGE = 1` 을 쓴다. 판독 결과의 페이지는
`team-result-adapter` 가 `context.pageIndex` 로 다시 찍으므로 문서 페이지 정보를
잃지 않는다. 시험은 `pageIndex: 4` 픽스처로 고정했고, 수리를 빼면 실패한다(확인).

### ② 미병합 중복 — 여전히 열림, 전제 조건 그대로

17차의 결론(라벨+크기로는 진짜 반복 기기와 쪼개진 판독을 못 가른다)이 그대로다.
20차의 PDF 직접 투입에서도 `MOLD TR-2`·`MOLD TR-3` 이 두 번씩 잡혔고, 이제는
벡터·래스터 **두 출처**에서 온다. 다시 풀려면 **정답 라벨이 붙은 근접쌍 데이터**
부터 만들어야 한다는 전제는 바뀌지 않았다. 이번 차수에서는 손대지 않았다.

### ③ 조각비 3배 — **내 지표의 결함이었다 (19차 정정)**

19차에 "고급 조각비가 0.041~0.057 대 0.115~0.149 로 구간이 안 겹친다"고 적고,
이것을 "이 자가 라벨 점수보다 갈라낸다"의 근거로 삼았다. **그 분리는 허상이었다.**

원인: `sliverRatio` 가 종류별 **중앙값 하나**를 정상 크기 기준으로 썼다. KIMM
도면의 `breaker` 는 크기가 뚜렷한 이봉분포다 —

```
지정문자 無  등가변: 13 13 15 18 18 19 20 20 20 21 21 21 21 22 25 | 48 48 48 48 48 48 48 61 61 63 63
지정문자 有  등가변:  9  9  9  9  9  9  9  9 11 15 18 19 20        | 40 40 40 40 40 40 40
```

작은 쪽은 피더 표의 MCCB, 큰 쪽은 VCB·ACB draw-out 이다. 중앙값이 두 봉우리
사이에 앉으면 **작은 쪽 기기 전체가 조각으로 오탐**된다. 조각 24건 중 대부분이
`breaker` 였던 것이 그 흔적이다.

수리: 크기를 정렬해 가장 큰 비율 틈(면적 4배 이상)에서 두 군집으로 나누고 각자의
중앙값을 기준으로 쓴다. 단 **군집은 인원을 요구한다** — 양쪽 2개 이상, 작은 쪽이
전체의 20% 이상일 때만 인정한다. 이 결박이 없으면 홀로 떨어진 조각 하나가 자기를
"작은 기기 군집"으로 선언해 스스로를 정상으로 만든다(첫 판이 실제로 그랬다).

`p25` 로 낮추는 방법도 재봤고 기각했다 — 고급 오탐은 죽지만 **중급의 진짜 조각
검출까지 죽였다**(7/2/4 → 0/1/0). 임계값이 아니라 기준이 하나뿐인 것이 문제였다.

수리 후 같은 데이터:

| 고급 조각비 | 19차(결함 지표) | 21차(수리 후) |
|---|---|---|
| 지정문자 無 | 0.041~0.057 | **0.021~0.057** |
| 지정문자 有 | 0.115~0.149 | **0.020~0.113** |
| 판정 | 구간 안 겹침 | **구간 겹침 → 차이 없음** |

**19차의 "이 자가 갈라낸다" 근거 중 조각비 부분은 철회한다.** 남는 근거는
`unmergedPairRatio` 다 — 명판 병합이 고급 미병합비를 0.014~0.159 → 0~0.009 로
접은 것은 지표 수리와 무관하게 유효하다.

그리고 18차의 "고급에서 지정문자 분기 효과 미확인" 상태도 그대로다. 조각비로
잡았다고 여겼던 차이가 사라졌으므로, **지정문자 수리가 고급에 미친 영향은
여전히 측정되지 않았다**(해롭다는 증거도, 이롭다는 증거도 없다).

## 22차 남은 과제 ①~⑥ — 정답 라벨을 만들고 판별식을 다시 세웠다 (2026-08-05)

### ① 정답 앵커 — 병목을 열었다

17차와 PROJECT_STATE S1 이 같은 벽에 막혀 있었다: "이 두 판독이 같은 기기인가"의
정답이 없었다. KIMM p5 는 네이티브 CAD 벡터 PDF(텍스트 858항목)이므로 **도면 자신의
텍스트 층**이 결정론적 정답이다.

```bash
npx tsx scripts/build-vector-anchor.mts fixtures/drawings/realworld/incoming/kimm-20210602-design.pdf 5 fixtures/drawings/realworld/labels/kimm-20210602-design-p5.vector-anchor.json
```

앵커 197건. 한계를 파일 안에 박았다 — `provenance: pdf-vector-text-layer`, **사람 2인
블라인드 판정이 아니다.** "도면이 무엇을 어디에 적었는가"의 정답이지 "그 자리에 어떤
물리 기기가 있는가"의 정답이 아니다. 분류 폴백(`load`)은 제외했다(858건 중 661건이
폴백이고 "110V" 같은 제원 문자가 전부 거기로 떨어진다) — **완전한 목록이 아니라
확실한 목록**이다.

### ② 판별식 재보정 — 겹침이 해로운 신호였다

두 판독이 같은 앵커에 붙으면 같은 기기로 라벨링해 **근접쌍 83건**(SAME 20 ·
DISTINCT 63)을 채점했다.

| 규칙 | 맞게 병합 | **잘못 병합** | 놓친 병합 | 맞게 유지 |
|---|---|---|---|---|
| 17차: 면적비≥1.5 **또는 겹침** | 18 | **19** | 2 | 44 |
| 겹침 단독 | 9 | **16** | 11 | 47 |
| 면적비≥1.5 단독 | 14 | 5 | 6 | 58 |
| 면적비≥2.0 단독 | 13 | 3 | 7 | 60 |
| **면적비≥5.0 단독(채택)** | 6 | **0** | 14 | 63 |

**DISTINCT 63건 중 16건이 겹친다** — 조밀한 피더 표에서는 이웃 기기 상자가 서로
겹친다. 17차에 이것을 안전한 신호로 보고 넣은 것이 오병합을 4배(5→19)로 늘린
주범이었다. 겹침 조건을 뺐다.

보수적인 5.0 을 택한 이유: 두 오류의 무게가 다르다. **놓친 병합은 중복이 남아 과다
계수로 보이지만 검토자가 도면에서 확인할 수 있고, 잘못된 병합은 실재하는 기기를
조용히 지운다.**

### ②의 라이브 격리 — 같은 번들, 병합 절만 on/off

앞선 측정에서 라벨 점수가 내려갔는데 그 사이에 ⑥ 수리도 들어가 귀속이 불가능했다.
그래서 **나머지 코드가 완전히 동일한** 두 팔로 다시 쟀다.

| 고급(KIMM) | 병합 없음 | 병합 있음 |
|---|---|---|
| 라벨 | 80~91% (폭 11) | **83~87% (폭 4)** |
| 변압기(정답 3) | 20 / 5 / 18 | **10 / 12 / 7** |
| 차단기(정답 9) | 31 / 14 / 20 | **18 / 21 / 15** |
| 미병합비 | 0.124 | **0.045** |
| 모호비 | 0.606 | 0.497 |

| 중급 | 병합 없음 | 병합 있음 |
|---|---|---|
| 라벨 | 86~100% (폭 14) | **92~96% (폭 4)** |
| 퓨즈(정답 15) | 15 / 15 / 16 | 15 / 14 / **20** |
| switch(정답 1) | 1 / 1 / **11** | 2 / 2 / 1 |
| 조각비 | 0.118 | **0.063** |

**두 티어 모두 최악값이 오르고 폭이 크게 줄었다**(고급 80→83·폭 11→4, 중급
86→92·폭 14→4). 미병합비 0.124→0.045 는 실제로 접었다는 직접 증거다.

정직하게 남길 것: 중급 한 회차가 퓨즈 20 으로 병합 없음 팔의 어느 회차보다 나쁘다.
그리고 고급은 여전히 정답 3 에 7~12 로 과다 계수한다 — **개선이지 해결이 아니다.**
팔당 n=3, 모델 1개, 도면 2장이다.

### ③ 떠 있는 조각 — 갇힌 표기와 다른 현상이었다

실측: 조각 78건이 **전부 본체 밖**이라 `demoteContainedMarkings` 가 하나도 못 잡는다
(갇힌 표기는 중급 전용 현상이었다). 대부분 명판을 가졌고 숫자 라벨은 4건뿐이다.
②의 병합이 중급 조각비를 0.118→0.063 으로 절반 이하로 줄였지만 **고급은
0.102→0.101 로 그대로다.** 고급의 떠 있는 조각은 미해결로 남긴다.

### ④ 지정문자의 고급 영향 — 여전히 미측정

21차에서 조각비 신호가 지표 결함으로 판명된 뒤, 이번 차수에서 별도 격리를 하지
않았다. 해롭다는 증거도 이롭다는 증거도 없는 상태 그대로다.

### ⑤ 측정력 — 정답 앵커 채점이 답이었다

라벨 점수는 고급에서 같은 코드로도 폭 15p 를 낸다. 반면 **정답 앵커 근접쌍 채점은
오병합 19 대 0 을 명확히 갈랐다.** 판별식 튜닝의 정본 계기는 라벨 점수가 아니라 이쪽이다.

### ⑥ PDF 직접 투입 — 수리 확인 완료

| | 수리 전 | 수리 후 |
|---|---|---|
| 구획 | 계획 17 · 완료 14 · **실패 3** | 계획 17 · 완료 16 · **실패 1** |
| 실패 사유 | 3건 모두 `rescanTargets[1] 값이 현재 도면 범위를 벗어났습니다` | `coverage audit found graph conflicts` (감사기가 제 일을 한 것) |
| 관계 | 425 | **524** |
| 호출 | 110 | 85 |

페이지 번호 원인 실패 3건이 사라졌다. 남은 1건은 원인이 다르다.

## 23차 고급 과다 계수 — 원인 셋을 갈라 둘을 잡았다 (2026-08-05)

22차까지 고급은 "정답 3 에 7~12" 로 과다 계수했다. 원본을 잘라 육안 확인하고
벡터 텍스트를 전수로 훑어 **원인이 하나가 아니라 셋**임을 갈랐다.

### ① 교보재 정답이 틀렸다 — 변압기는 3 이 아니라 4다

원본 래스터를 잘라 확인했다:

- **MOLD TR-1 · TR-2 · TR-3** — Δ-Y 심볼 3대(6.6kV/220V·440V·380.220V)
- **DOWN TR 380/110V 3∅ 10KVA** — DC반에 Δ-Y 심볼로 **실재하는 4번째 변압기**

종전 정답 `transformer: 3` 은 MOLD 계열만 세어 DOWN TR 을 빠뜨렸다. **정답을 맞게
읽은 실행이 오히려 오답으로 채점되고 있었다.** `run-drawing-model-matrix.mjs` 와
`run-drawing-effort-calibration.mjs` 의 고급 기대값을 4 로 정정했다.

같이 확인한 것 — 기기가 **아닌** 것 둘:

- 육각형 `TR` 마커 3개: 도면 참조 콜아웃이다(아래 ②).
- `TR FL&FAN`: 표의 **FEEDER NAME 열** 값이다(QE0B MCCB 의 부하 이름). 기기가 아니다.

### ② 벡터 파서가 참조 콜아웃을 기기로 셌다 — 수리함

벡터 텍스트를 좌표째 훑으니 서명이 깨끗했다:

```
마커    "1"@11.9,30.0 + "TR"@11.8,30.5      ← 이 둘이 전부다
마커    "2"@32.0,30.0 + "TR"@31.9,30.5
마커    "3"@52.0,30.0 + "TR"@51.9,30.5
실기기  "CH" "(표준소비효율)" "MOLD TR-1" "6.6KV/220V" "E1" "3∅ 500KVA" "(혼촉방지판 내장)"
실기기  "DOWN TR" "380/110V" "3∅ 10KVA" "E3"
```

**홑 숫자 바로 아래 붙은 짧은 약호**가 콜아웃 서명이다. 결박 셋으로 정당한 기기를
지키게 했다 — 제원(전압·전류·용량)이 붙으면 제외, 약호가 5자 이상이면 제외, 숫자가
같은 x·바로 위(페이지 높이 1.5% 이내)에 있어야 인정.

**전수 확인(같은 페이지 기기 텍스트 197건): 제거 3건 — 전부 육각형 TR 마커였고
`CH`·`PL`·`SC` 같은 약호 기기는 하나도 걸리지 않았다.** 벡터 변압기 8 → 5.

| | 수리 전 | 수리 후 | 정답 |
|---|---|---|---|
| 벡터 경로 변압기 | 8 | **5** | 4 |

남은 1건이 `TR FL&FAN` 이다. 표의 열 위치를 봐야 가려낼 수 있어 이번엔 손대지 않았다.

### ③ 라스터 중복 — 벡터 앵커 스냅이 답이지만 PNG 경로에는 앵커가 없다

라스터 확정 판독을 벡터 앵커로 스냅하는 시뮬레이션에서 **변압기 앵커 4~5 · 차단기
앵커 8~11**(정답 4 · ≥9)이 나왔다. 그런데 적용 범위가 갈린다:

| 업로드 | 벡터 패스 | 앵커 |
|---|---|---|
| PDF | 발화(hybrid) — 심볼 166개가 `vector-full` 근거를 가짐 | **있음** |
| PNG(매트릭스 고급 티어) | 미발화 | 없음 |

매트릭스 고급 티어는 래스터 PNG 를 올리므로 이 경로를 타지 않는다. 즉 **스냅 병합은
실제 사용 흐름(CAD PDF 업로드)에서만 값이 있고 현재 벤치마크로는 측정되지 않는다.**
구현은 하지 않았다 — 측정할 수 없는 것을 넣지 않는다.

### 남은 것

- `TR FL&FAN` 류: 표 열 인식 필요.
- 라스터 전용 경로의 중복: 앵커가 없으므로 22차의 명판 병합(면적비 ≥5)이 현재 최선이다.
- 면적비는 근본적으로 약한 신호다 — 정답 83쌍에서 SAME 1.00~10.10, DISTINCT
  1.00~4.97 로 완전히 겹친다. 라스터 전용 도면의 중복 판별은 다른 신호가 필요하다.

## 24차 과다 계수의 진짜 출처 — 병합이 아니라 계수 등록기였다 (2026-08-06)

17차부터 23차까지 고급 과다 계수를 **병합 실패**로 보고 판별식을 세 번 고쳤다.
추적해 보니 출처가 다른 곳이었다.

### 추적

```
그래프의 전력변압기 노드      5~8
채점기가 보고한 값            11
```

채점기(`scripts/lib/local-drawing-receipt.mjs`)는 심볼 집계를
`equipmentCounts.physicalEquipmentCount` 로 **덮어쓴다**(`Object.assign`). 그 값이
11 이었다. `count-register` 의 `normalizeKind` 는 일반 분기
`t.includes('transformer')` 로 끝나는데, 앞의 특수 분기가 세 이름을 안 잡았다:

| 타입 | 종전 집계 | 실제 |
|---|---|---|
| `instrument_transformer` (4건) | 전력변압기 | 계기용변성기 |
| `potential_transformer` (3건) | 전력변압기 | 계기용변압기(PT) |
| `vt_pt` | 전력변압기 | 계기용변압기 — **중복 병합기가 PTx3·PPT 명판에 붙이는 정본 타입이다** |

5~8 + 7 ≈ 11. 숫자가 맞는다. 전기적으로도 틀린 계수다 — 계기용변성기는
전력변압기가 아니고, 검토자는 없는 변압기를 찾게 된다.

**같은 결함이 `transformer_ct`·`transformer_vt` 에 대해 이미 한 번 수리돼 있었다**
(기존 시험 주석에 이력이 남아 있다). 이름이 다른 셋이 그물을 빠져나갔다.

### 라이브 결과

| 티어 | 수리 전 | 수리 후 |
|---|---|---|
| **advanced(PNG) 라벨** | 83~88% | **92~95%** |
| advanced 변압기(정답 4) | 15 / 8 / 8 | **6 / 5** |
| advanced-pdf 라벨 | 85~92% | 87~90% |
| advanced-pdf 변압기(정답 4) | 11 / 6 / 11 | **8 / 9 / 7** |

**PNG 티어의 +9p 는 깨끗하게 귀속된다** — PNG 는 벡터 패스를 아예 타지 않으므로
같은 기간의 다른 수리(참조 콜아웃)가 영향을 줄 수 없고, 계수 등록기 변경이 유일한
차이다. 이번 세션에서 가장 큰 단일 개선이고, **판독 결함이 아니라 계수 결함에서 나왔다.**

정직하게: advanced 3회 중 1회가 `ERROR`(지속시간 28618s)로 끝났다. 660초 HTTP
상한을 훨씬 넘는 값이라 실행 중 장비 절전·연결 끊김으로 보이지만 **원인을
확인하지 않았다.** 위 92~95% 는 완료된 2회의 값이다.

### 측정 수단을 먼저 세웠다 — `advanced-pdf` 티어

기존 `advanced` 는 같은 페이지를 **래스터 PNG** 로 올려 벡터 패스를 타지 않는다.
실제 사용 흐름(CAD 가 출력한 PDF 업로드)이 벤치마크에서 빠져 있었다. 케이스별
`pages` 선택과 함께 티어를 세웠다(83p 설계세트에 `all` 을 보내면 안 된다).

```bash
node --env-file=.env.local scripts/run-drawing-model-matrix.mjs --tiers=advanced-pdf --models=gemini --repeat=3
```

첫 측정에서 **차단기 70~92** 가 나왔다. 과다가 아니라 **피더 표의 MCCB 를 실제로
읽은 것**이다(PNG 경로는 17~23). 정답이 `minimumSymbolTypes: {breaker: 9}` 라
양쪽 다 통과하지만, 실제 기기 수는 PDF 경로가 훨씬 가깝다.

### 23차의 "측정 불가" 를 정정한다

23차에 "벡터 앵커 스냅은 측정할 수 없어서 구현하지 않았다" 고 적었다. **측정 수단을
만들면 되는 것을 안 만든 것이었다.** 티어를 세우고 재보니 결론은 같지만 근거가 바뀐다:

- 벡터와 같은 타입·근접인데 **안 접힌** 라스터 노드는 121개 중 **8개**(허용 40px)다.
- 허용을 120px 로 넓히면 19개가 되지만, 이 도면의 실기기 간격이 ~50px 라 오병합
  위험이 급증한다.
- **기존 병합이 이미 대부분 잡고 있다**(벡터·라스터 근거를 함께 가진 노드 50개).

즉 구현하지 않는 이유가 "잴 수 없다" 가 아니라 "재보니 여지가 작다" 다.

## 25차 유일 명판 병합 — 실제 사용 흐름에서 95%·폭 0 (2026-08-06)

24차 계수 수리 뒤에도 전력변압기가 정답 4 에 5~9 였다. 그래프를 열어 보니 남은
것이 전부 **같은 명판을 1~3% 거리에서 두세 번 읽은 것**이었다:

```
"MOLD TR-2 6.6kV/440V 3 1000kVA" @42,29
"MOLD TR-2 1000kVA"              @40,30   ← 같은 기기
"DOWN TR 380/110V 3~ 10KVA"      @78,48
"DOWN TR 380/110V 10kVA"         @79,49   ← 같은 기기
```

크기가 비슷하고 겹치지도 않아 종전 규칙(면적비 ≥5 · 겹침 · 근접) 어느 것에도 안
걸린다. **22차 정답 채점에서 면적비가 SAME 1.00~10.10 · DISTINCT 1.00~4.97 로
완전히 겹친 이유가 이것이다 — 크기는 근본적으로 약한 신호다.**

### 강한 신호는 도면 자신의 선언이다

벡터 층이 `MOLD TR-2` 를 **딱 한 번** 선언했다면 그 이름을 단 판독은 몇 개든 한
대다. 간접 신호가 필요 없다. 반대 방향도 같은 근거로 지켜진다:

| 명판 | 벡터 앵커 수 | 동작 |
|---|---|---|
| `MOLD TR-2` · `DOWN TR` | 1 | 접는다 |
| `VCB(DRAW OUT)` | 5 | 안 접는다(실재 5대) |
| `MCCB ABSc` | 78 | 안 접는다(피더 표 행마다 하나) |

벡터 판독이 없는 원본(래스터 이미지 업로드)에서는 유일 명판 집합이 비어 규칙이
발화하지 않는다 — **도면이 말해 주지 않으면 추측하지 않는다.**

### 라이브 결과 (gemini · 3회)

| `advanced-pdf` (실제 사용 흐름) | 24차 | 25차 |
|---|---|---|
| 라벨 | 87~90% (폭 3p) | **95 / 95 / 95% (폭 0p)** |
| 전력변압기 (정답 4) | 8 / 9 / 7 (폭 2) | **5 / 5 / 5 (폭 0)** |
| 차단기 (정답 ≥9) | 70 / 91 / 92 | 77 / 84 / 80 |

**폭 0 이 핵심이다.** 같은 도면을 세 번 넣어 같은 답이 나온다 — 이 세션 내내
못 하던 것이다. 남은 5번째 변압기는 `TR FL&FAN`(표의 FEEDER NAME 열 값)이고
23차에 이름 붙여 둔 별건이다.

`advanced`(PNG)는 86~95%(폭 9p)로 24차의 92~95%(2회)와 구간이 겹친다. PNG 는
벡터 앵커가 없어 이 규칙이 발화하지 않으므로 **차이는 실행 변동이다.**

### 이 세션 도면 정확도 이력 (고급 · gemini · 3회)

| 차수 | PNG | PDF |
|---|---|---|
| 22차 | 83~87% | — |
| 23차(콜아웃) | 83~88% | 85~92% |
| 24차(계수) | 92~95%\* | 87~90% |
| **25차(유일 명판)** | 86~95% | **95 / 95 / 95%** |

\* 24차 PNG 는 3회 중 1회가 ERROR 로 끝나 2회 값이다.

### 부수 진단 — 초급의 관계 확신도 (미수리)

초급(`wiki-oneline.png`) 6회를 훑으니 **관계 11~13개 중 확정은 0~1개**다. 나머지는
전부 `ambiguous` 다. 채점기는 총 관계 수만 세어 85~100% 로 통과시키지만 확신도로는
사실상 아무것도 확정하지 못한다. 고립 확정 기기는 전부 `arrow`·`source_load_arrow`
(전력흐름 화살표)로, 기기가 아니라 주석이다. 이번 차수에서 손대지 않았다.

## 26차 라스터 경로 수리와 타입 구분자 결함 (2026-08-06)

25차까지 "라스터(스캔·사진) 도면은 못 쓴다" 고 말만 하고 그 자리를 안 고쳤다.
유일 명판 판정이 벡터 앵커에만 의존했기 때문인데, **라스터에도 OCR 문자 층이 있다.**

### ① 문자 중복 제거가 아예 없었다

`assignDisplayIdsForTexts` 는 정렬 후 ID 만 붙였다. 구획이 겹치게 잘리므로 같은
명판이 2~3 노드로 남았다:

```
"MOLD TR-2"  989,511 42x6   |  1027,514 67x10    ← x 4px 겹침, y 동일
```

같은 글자·같은 자리(겹치거나 글자 높이 한 칸 안쪽)면 하나로 접고 더 넓게 읽은
쪽을 남긴다. 피더 표의 `MCCB ABSc` 78 행은 서로 멀어 안 접힌다.

### ② 라스터에서도 명판 다중도를 센다

벡터 판독이 있으면 그것이 정본(도면이 직접 선언한 값), 없으면 정리된 문자 층으로
센다. 둘 다 없으면 발화하지 않는다.

### ③ 타입 구분자 — CT·ZCT 가 전력변압기로 세어졌다

`normalizeKind` 가 `includes('current_transformer')` 로 **밑줄형만** 검사했다.
모델은 `current transformer`(공백)도 낸다. 공백형은 특수 분기를 빠져나가 일반 분기
`includes('transformer')` 로 떨어졌다.

실측: 한 회차에서 `current transformer` 7개(`CTx3 160/5A`·`ZCT 200/1.5mA` 등)가
전력변압기로 세어져 5 대신 12 가 나왔다. **회차마다 모델이 어느 형태를 내느냐로
값이 흔들렸으므로 이 결함이 계수 변동의 출처이기도 하다.** 24차 수리와 같은
결함군인데 이름 형태만 달랐다.

### 라이브 (gemini · 3회)

| 티어 | ①② 만 | ①②③ |
|---|---|---|
| 고급 PDF | 84 / 95 / 95 (폭 11p) | **95 / 95 / 95 (폭 0p)** |
| 고급 PNG | 88~95% (폭 7p) | **88~92% (폭 4p)** |
| 중급 | 98~99% (폭 1p) | 75~100% (폭 25p) ← 아래 |

③ 이 PDF 의 폭 0 을 되돌렸다 — 회귀의 원인이 ③ 이었음이 확인된다.

### 중급 한 회차 붕괴(75%) — 우리 결함이 아니다

| 회차 | 호출 | 심볼 | 확정 퓨즈 | 모호 | 문자 |
|---|---|---|---|---|---|
| 1 | 60 | 21 | 17 | 2 | 84 |
| 2 | 47 | 27 | 15 | 10 | 94 |
| **3** | **34** | 25 | **3** | **20** | 64 |

판독은 정상(심볼 25)인데 판정이 무너졌다. 모호 20개를 열어 보면 **후보가 하나뿐인데도
모호**다(`["switch"] QS1`, `["fuse"] FU3`). 병합 경로는 후보가 충돌할 때만 강등하므로
이 상태는 **모델이 낮은 확신도로 준 것**이다. `AMBIGUOUS_OCR` 64건이 같은 것을 가리킨다.

과병합도 아니다 — 그 회차의 근거 4개 이상 노드는 **0개**다(정상 회차는 11개).

**수리 가능 여부: 깨끗한 수단이 없다.** 지렛대는 재스캔인데(붕괴 회차 34호출 대
정상 47~60), 재스캔을 더 거는 방향은 17차에 조밀한 도면을 악화시키는 것으로
확인됐다. 모델 확신도 변동을 우리 쪽에서 메우는 방법을 아직 못 찾았다.

## 27차 참조 도면 일반화 시험 — 교재형 수변전 단선결선도 (2026-08-06)

17~26차의 도면 수리는 **전부 KIMM 실도면 한 장으로 보정**됐다. 성격이 다른 도면에서
통하는지 보려고 참조 교보재(한글 라벨 교재형 22.9kV 수변전 단선결선도, p6)를 티어로
세웠다.

> 이 교보재는 재배포할 수 없어 `fixtures/drawings/local/`(gitignore)에 둔다.
> **파일도 원본 이미지도 이 저장소에 넣지 않는다**(로컬 자료 정책). 남기는 것은
> 측정 수치와 발견한 결함뿐이다. 매트릭스 티어 이름은 `reference-textbook` 이고
> `--tiers` 로 명시할 때만 실행된다.

정답은 원본을 확대해 육안으로 셌다: **수전용 변압기 3**(Δ-Y 3쌍) · 부하 3 · CB 1 ·
MOF 1 · PT 1 · CT 1 · LA 1 · DS 2 · PF/COS 2 · OCR 3 · OCGR 1 · A 1 · V 1.

### 첫 실행에서 결함 하나가 드러났다 — 줄바꿈된 한국어 주석

| | 수리 전 | 수리 후 |
|---|---|---|
| 라벨 | 92~94% (폭 2p) | **100 / 100 / 100% (폭 0p)** |
| 전력변압기(정답 3) | 4 / 2 / 4 | **3 / 3 / 3** |
| 미병합비 · 조각비 | 0.136 · 0.083 | **0.000 · 0.000** |
| 품질 판정 | FAIL | **HOLD** |

4번째 변압기의 정체는 **주석 문장**이었다. 주 6 이 두 줄로 잘려서:

```
① "…계통은 CNCV-W 케이블(수밀형) 또는 TR CNCV-W"   ← 종결 표현 없음 → 기기로 승격
② "(트리억제형)을 사용하여야 한다. 다만, 전력구"      ← 종결 표현은 여기에만
```

①의 `TR`(트리억제형 케이블 약호)이 **전력변압기로 계수**됐다. `isProseText` 의 한국어
판정이 종결 표현(`하여|합니다|해야`…)에만 의존했는데, 그것은 정의상 **마지막 줄에만**
있다. 줄바꿈된 주석의 앞줄은 전부 이 그물을 빠져나간다.

**수리**: 한국어는 교착어라 문장 속 낱말이 조사를 달고 나온다(`계통은`·`인입선의`·
`경우에`). 토큰 5개 이상 + 조사로 끝나는 토큰 2개 이상이면 문장으로 본다.

**전수 확인**: 이 교재 페이지의 기기 분류 문자 5건이 전부 걸리고(도면 제목·해설·주석
3줄 — 넷 다 실제로 문장이다), **KIMM 실도면 p5 의 기기 문자 197건은 하나도 걸리지
않았다.** 수리 뒤 KIMM 벡터 산출은 기기 236 · 변압기 5 · 차단기 104 로 **수리 전과
완전히 동일**하다.

### 일반화 판정

KIMM 한 장으로 보정한 수리들이 **성격이 전혀 다른 도면에서 100% 로 통했다**.
그리고 그 도면이 KIMM 에는 없던 결함(한국어 주석 승격)을 하나 더 드러냈다 —
교보재를 늘리는 것이 왜 필요한지 그 자체가 근거다.

같은 실행의 KIMM PDF 는 88~95%(폭 7p)로 26차의 95/95/95 보다 낮지만, 위에서 확인한
대로 **벡터 산출이 비트 단위로 같으므로 이 차이는 실행 변동이다.**

> **28차 정정**: 이 회차까지의 모든 종합 % 는 자가 헐거운 상태에서 나온 값이다.
> 아래 28차의 재채점 표를 정본으로 본다.

## 28차 자가 과다 계수에 상을 주고 있었다 (2026-08-07)

"이제 쓸만하냐"에 답하려고 수치를 다시 들여다보다 **채점기 자체의 결함**을 찾았다.
원장 규율이 정한 대로(`재실증 요구가 정당한 경우` — "게이트 자체의 결함 의심,
그 경우 게이트를 고치는 게 일이다") 게이트를 먼저 고쳤다.

### 결함 — 하한을 점수로 쓰고 있었다

`scripts/lib/drawing-model-score.mjs` 는 종합을 `기호 정확도 70% + 관계 회수율 30%`
로 냈고, 관계축이 `min(1, 실측/하한)` 이었다. 그런데 `minRelations` 는 **정답이 아니라
사람이 공개 그림을 직접 센 회귀 하한**이다(스크립트 주석에 그렇게 적혀 있다).
실측이 하한을 넘기만 하면 언제나 100% 다.

| 티어 | 관계 실측 / 하한 | 옛 관계축 |
|---|---|---|
| 고급 PDF | **463 / 12 = 38.58배** | 100% |
| 고급 PNG | 254 / 12 = 21.17배 | 100% |
| 중급 | 24 / 15 = 1.60배 | 100% |
| 참조 교재 | 32 / 10 = 3.20배 | 100% |

`minimumSymbolTypes` 도 같다 — 고급 PDF 의 차단기는 **78 / 9 = 8.67배**인데 100% 였다.

즉 **종합의 30% 는 무료였고, 과다 계수는 오히려 점수를 올렸다.** 17~27차 내내
쫓아온 결함이 과다 계수인데 자가 그것에 상을 주고 있었다. 24차(계수 등록기)·
26차(타입 구분자)와 같은 자리다 — **코드보다 자가 먼저 틀려 있었다.**

### 시험이 결함을 계약으로 굳히고 있었다

`drawing-model-score.node-test.mjs` 의 첫 시험 이름은 `…70/30 으로 합산한다` 였고,
관계 9 vs 하한 12 처럼 **하한 미달만** 넣어 봤다. 하한을 넘긴 경우를 한 번도 넣지
않았으므로 무료 100% 가 드러날 수 없었다. 시험을 고쳐 그 구멍을 메웠다.

### 수리

하한은 점수가 아니라 **관문**으로 분리한다.

- 종합은 정답 수량을 아는 축(`symbolTypes`, exact)만으로 매긴다.
- 하한(`minimumSymbolTypes`·`minRelations`)은 `floorGates` 로 충족 여부와 **초과 배율**만
  낸다. 정답 상한을 모르므로 초과를 감점하지 않되 100% 로 뭉개지도 않는다.
- 정확 축이 하나도 없으면 `null` 이다. 점수를 지어내지 않는다.

**판별 확인(A/B)**: 옛 자를 되돌리면 새 시험 5개 중 **4개가 red**, 새 자에서 5/5 green.

### 재채점 — 실행 없이, 저장된 영수증의 원시 수량으로

영수증에 타입별 실측이 그대로 있어 VLM 재호출 없이 다시 채점했다.

| 티어 | 옛 종합 | **새 종합** | 하한 관문 | 확정/기호 | 모호비 | 품질 |
|---|---|---|---|---|---|---|
| 참조 교재 | 100% | **100%** | OK | 12/30 | 0.60 | HOLD |
| 초급 | 95% | **100%** | **FAIL** (관계 11/13) | – | – | FAIL |
| 고급 PDF | 88% | **75%** | OK | 206/293 | 0.30 | FAIL |
| 고급 PNG | 88% | **75%** | OK | 69/172 | 0.60 | FAIL |
| 중급 | 75% | **64%** | OK | 5/25 | 0.80 | FAIL |

초급이 95→100 으로 **오른** 것이 이 수리의 성격을 잘 보여 준다. 기호는 전부 맞았고
관계만 하한 미달인데, 옛 자는 그 둘을 95% 라는 한 숫자에 섞어 **미달을 지웠다**.
이제 정확도는 100% 로, 관문 실패는 실패로 각각 보인다.

### 그래서 지금 상태 (실측 기준)

| 축 | 상태 | 근거 |
|---|---|---|
| 깨끗한 교재형 도면 계수 | **쓸 수 있다** | 100%, 폭 0p, 조각·미병합 0.000, 품질 HOLD |
| 실도면(KIMM) 계수 | **아직 아니다** | 75%. 변압기 정답 4 에 **8** — 2배 과다 |
| 결선 판정 | **재고 있지 않다** | 하한 관문뿐. 정답 간선표가 없어 정확도 미측정 |
| 판독 확신도 | **낮다** | 모호비 0.30~0.80. 100% 인 참조 티어도 30개 중 확정 12 |

**결선축은 "수리 안 됨"이 아니라 "측정된 적 없음"이다.** 26차의 초급 진단(관계 11~13
중 확정 0~1)과 같은 것을 티어 전체에서 확인한 셈이다. 이 축에 자를 대려면 도면 하나에
대한 **정답 간선표**가 필요하고, 그것은 27차의 벡터 앵커처럼 도면 자체에서 뽑아야 한다.

### 앵커

- 커밋: 이 항목과 같은 커밋.
- 재실행: `npm run test:scripts` (판별 A/B 는 `scripts/lib/drawing-model-score.mjs` 를
  이전 커밋 판으로 되돌리면 5개 중 4개 red).
- 재채점 입력: `test-results/drawing-model-high-gemini-*.json` (27차 실행 영수증).

## 29차 얇은 정답표와 별칭 표의 구멍 (2026-08-07)

28차에서 참조 교재 티어만 100% 로 남았다. 그런데 그 100% 가 무엇을 재고 있었는지
보니 **정확 축이 사실상 하나**였다 — `transformer 3` 과 `generator 0`(자명한 축),
그리고 하한 관문 둘. 27차에 육안으로 센 정답은 13종인데 정답표는 그중 3종만
걸고 있었다.

### 정본 어휘가 있는 축만 넓혔다

`canonicalSymbolType` 이 별칭을 접는 축은 breaker·switch·arrester·transformer
넷뿐이다. MOF·PT·CT·PF/COS·OCR·OCGR·A·V 는 모델이 부르는 대로 흘러나오므로
정답표에 넣으면 판독이 아니라 **이름 불일치**를 채점하게 된다(26차 구분자 결함과
같은 함정). `부하 3` 도 뺐다 — `load` 는 분류 실패의 흡수통이다.

그래서 `breaker` 를 하한 1 → **정확 1** 로 조이고, `switch 2`(DS)·`arrester 1`(LA)
을 더했다. 정답표는 채점에만 쓰이고 요청에는 들어가지 않으므로(`runCell` 이 보내는
것은 파일·공급자·모델·effort·페이지뿐) 판독에는 영향이 없다.

### 넓히자 무너졌다

| | 라벨 | 폭 |
|---|---|---|
| 27차 (얇은 정답표) | 100 / 100 / 100% | 0p |
| **넓힌 정답표** | **45 / 86 / 65%** | **41p** |

`transformer 3/1/3` · `breaker 1/2/1` · `switch 8/5/7` · `arrester 0/0/1`.
**27차의 "폭 0p" 는 실질 축 하나짜리 정답표 위에서 나온 값이었다.**

### 원인은 판독이 아니라 별칭 표였다 — 같은 결함 셋

영수증의 `evidenceGraph.symbols` 를 열어 보니 피뢰기는 **읽혀 있었다**.

```
lightning_arrester|surge_arrester|arrester   ambiguous   "LA"
```

`actualSymbolTypes` 는 `typeCandidates[0]` 만 정본화한다 → `lightning_arrester`
→ 정규화 `lightningarrester` → 별칭 `['arrester','surgearrester','spd']` 에 없음
→ 골든 축 0. **후보 목록 안에 `arrester` 가 있는데 무시됐다.**

같은 페이지에 하나 더 있었다 — 단로기가 `disconnecting_switch` 로 나오는데 그것도
별칭에 없어 switch 축에서 빠진다. 26차 `current transformer`(공백형)까지 합치면
**같은 결함의 세 번째 사례**다.

> 이 둘은 성격이 반대라 발견 난이도가 다르다. 피뢰기는 축이 **0 이 되어** 눈에
> 띄었지만, 단로기는 축에서 빠지면 **과다 계수가 줄어 점수가 올라간다.**
> 즉 **누락이 스스로를 감춘다.** 별칭 표는 반드시 양방향으로 시험해야 한다.

### 수리와 재측정

`lightningarrester`·`la` 를 arrester 에, `disconnectingswitch`·`ds` 를 switch 에
넣었다. 판별 A/B: 각 별칭을 빼면 해당 시험이 red(각 1건), 넣으면 56/56 green.

| 단계 | 라벨 | 폭 | 어긋난 축 |
|---|---|---|---|
| 넓힌 정답표 · 별칭 결함 | 45~86% | 41p | transformer·breaker·switch·arrester |
| + 피뢰기 별칭 | 86~100% | 14p | switch 7/2/2 |
| **+ 단로기 별칭** | **85~100%** | **15p** | **switch 4/2/8** |

단로기 별칭을 넣으면 축 인원이 늘어 점수가 내려간다. 그 방향이 맞으므로 그대로 뒀다.
transformer·breaker·arrester 는 세 축 모두 3회 전부 정답과 일치한다.
한 회차는 **switch 까지 정확히 2 로 100%** 다 — 파이프라인이 이 페이지를 정확히
읽을 수 있다는 뜻이고, 다만 **그것을 매번 하지는 못한다**(폭 15p).

### 남은 결함 — 진단됐고 미수리

**① `typeCandidates[0]` 임의 채택.** 모델이 스스로 못 정한 후보의 첫 번째를 쓴다.

```
switch|fuse   confirmed   "PF 10[kA]이상"   ← 전력퓨즈인데 switch 로 세어진다
```

피뢰기는 별칭으로 우회했지만 이건 구조 문제다. 후보 중 골든 축에 맞는 것을 고르게
바꾸면 `switch|fuse` 처럼 **둘 다 골든인 경우**에 다시 임의 선택이 된다.

**② 공백 차이로 같은 기기가 둘로 남는다.**

```
switch|fuse   ambiguous   "COS 또는 PF"
fuse          confirmed   "COS또는PF"     ← 공백만 다르다
```

**③ 라벨 없는 switch 유령.** 실측 8 회차의 8개 중 라벨이 있는 것은 DS 2 개뿐이다.
정답표가 틀린 게 아니라 빈 라벨 기기를 만들어 내고 있다.

> **30차 정정: ③ 은 오판이다.** 원본을 확대해 보니 그 "유령"들은 **모선에서 갈라진
> 피더 3개의 개폐기로 실재한다.** 정답표가 틀린 게 맞았고(27차 `PF/COS 2` 가
> 오답), 파이프라인의 정상 판독을 오류로 채점하고 있었다. ① 도 재검토했다 —
> `normalizeLabel` 은 이미 공백을 지우므로 병합을 막은 것은 공백이 아니라
> 타입 불일치다. 아래 30차 참조.

## 30차 정답표를 원본으로 재검수하고, 감사 소견이 판독을 버리던 것을 고친다 (2026-08-07)

29차의 `switch 8/5/7` 을 결함으로 적었는데, 원본을 확대해 확인하니 **내 정답표가
틀렸다.**

### ① 내가 기기를 빠뜨렸다

모선에서 갈라진 **피더 3개의 개폐기**를 27차 육안 계수에서 통째로 놓쳤다. 각
피더가 개폐기 → 변압기 → 부하로 이어지는데, 그 개폐기 3대가 `PF/COS 2` 안에
없었다. 실제는 **곡선 블레이드 5대**(PF 10[kA] 1 + COS또는PF 1 + 피더 3)다.

**나는 파이프라인의 정상 판독을 오류로 채점하고 있었다.** 29차에 "유령"이라고
쓴 것은 실재하는 기기다.

### ② `switch` 축은 이 도면에서 잴 수 없다

정확 수량 축의 조건은 어휘만이 아니었다.

| 조건 | 내용 |
|---|---|
| ① 어휘 | `canonicalSymbolType` 이 별칭을 접는 축일 것 (29차에서 세운 조건) |
| ② **결정성** | **도면이 그 클래스를 결정할 것** (30차에서 추가) |

이 교재는 PF·COS·피더 개폐기에 **전부 같은 곡선 블레이드 기호**를 쓰고, 라벨이
`COS또는PF`(둘 중 하나)다. 도면만으로 switch/fuse 를 가를 수 없으므로 어느 수를
걸어도 자가 아니라 추측이다. **파이프라인이 `ambiguous` 로 남기는 것이 맞는
동작이다.** 축에서 뺐다.

정답표는 `transformer 3 · generator 0 · breaker 1 · arrester 1` 넷이 됐다.
이것으로 재측정하니 **83~100%(폭 17p)**, 어긋난 축은 `transformer 1/3/1` 하나였다.

### ③ 원인 — 감사 소견이 판독을 버리고 있었다

호출 수가 원인을 지목했다.

| 회차 | 호출 | 라벨 | 변압기 |
|---|---|---|---|
| 1 | **34** | 83% | **1** |
| 2 | 66 | 100% | 3 |
| 3 | **34** | 83% | **1** |

34호출 회차의 전면 판독(`p5-full`) 기록:

**실질 역할 넷이 전부 성공했는데 감사자 하나 때문에 전면 판독 전체가 failed** 가
되고 페이지가 `PAGE_ANALYSIS_PARTIAL` 이 된다. 전면 판독은 변압기 3대를 한 시야에
보는 유일한 패스인데 그것이 버려지니 구획 조각만 남아 1대가 된다.

그리고 판정이 **두 곳에 따로 있고 서로 반대**였다.

BLOCKING = {UNBOUND_LINE_ENDPOINT, SELF_LINE_ENDPOINT}

정본 집합이 "모호성은 HOLD" 라고 선언하는데 정규식이 무시했다. 이 저장소에

있는데도** 그 규칙이 오케스트레이터에 닿지 않았다.

면책 문구였고 **이제는 측정된 사실이다.**

### ① 31차의 "어휘를 닫았다" 는 과장이었다

중복 제거기가 **둘**이다. 실제로 문서를 만드는 쪽
(`document-orchestrator` → `evidence-deduplicator`)은 그래프 입구를 거치지 않고
날 판독(`RawSymbolHit`)을 직접 받는다. 거기 사설 별칭 표가 그대로 있었다.

```
current_transformer  (전면 판독)  → 'current_transformer'
ct                   (구획 재판독) → 'ct'          ← 서로 다른 값 → 같은 CT 가 두 노드
```

`typesCompatible` 을 **계열 비교**로 올리고 정본에 연결했다. 시험 4건이 깨졌고
**하나는 우연히 통과하고 있던 것**이었다 — `does not merge overlapping PT/PPT` 가
`pt` 와 `ppt` 를 "다른 타입" 예시로 썼는데 **둘 다 계기용변압기이고 좌표가 완전히
같았다**(구획 둘이 같은 자리를 읽은 것). 병합이 맞다. 옛 별칭 표에 둘 다 없어서
서로 다른 값이 되는 바람에 통과하고 있었다. 이 시험이 지키려던 것(계열이 다르면
겹쳐도 안 붙는다)을 실제로 검사하도록 입력을 `transformer` vs
`current_transformer` 로 바꿨다.

### ② 관계 조립기도 둘이었고, 7차는 한쪽만 고쳤다

`spatial-graph` 의 관계 조립기는 **단일 선분의 양끝이 각각 정확히 한 기기에 닿을
때만** 관계로 인정한다. 실제 단선결선도는 기기 → 분기점 → 모선 → 분기점 → 기기로
가므로 **모선 구간처럼 양끝이 기기가 아닌 정상 도선이 전부 `UNBOUND_LINE_ENDPOINT`**
로 신고되고, 감사자가 페이지를 실패시킨다.

| | `evidence-deduplicator.buildPageRelations` | `spatial-graph` edges |
|---|---|---|
| 도선 위 여러 기기 | `orderedSymbolsOnConductor` | 없음 |
| 선망 추적 | `buildLineAdjacency`·`connectedLineIds` | 없음 |
| 분기→모선 브릿지 | 있음 | 없음 |
| 조각난 도선 복원 | 최소 신장 트리 | 없음 |
| **결과** | **관계 30개** | **UNBOUND/SELF → 페이지 FAIL** |

7차가 고친 것은 왼쪽뿐이다.

**수리**: 조립기를 옮기지 않았다(자료형이 다르다). 대신 **거짓 UNBOUND 를 없앴다** —
끝점이 분기점·교차점에 닿으면 선망에 이어진 것이고, 모선 위 구간은 자기 참조가
아니다. **아무것도 안 닿은 부유 끝점은 그대로 신고**하므로 차단 신호는 살아 있다.

> 기존 4,160개 시험 중 이 변경을 잡는 것이 **하나도 없었다.** 모선 구간이라는
> 정상 경우를 아무도 시험하지 않았다. 새 시험 4개 중 둘이 차단 신호 생존을 지킨다.

### ③ 침묵 실패 둘 — 실행 실패가 성능 수치로 둔갑하고 있었다

Gemini 키가 삭제돼 GPT 경로로 돌렸더니 **라벨 25% · 관계 0% · 조립 지표 전부 0.000**
이 나왔다. 원장 6차에 같은 숫자가 있다 — 스키마 결함으로 51호출이 일괄 실패해
**23%·관계 0%**. 성능처럼 보이지만 실행 실패다.

실제로 구획 10/10 failed · `rolesPresent []` · 기호 0 · 전 역할
`LOCAL_CODEX_TURN_FAILED` 였다. 그런데 **원인을 두 번 버리고 있었다.**

| 버린 곳 | 무엇을 |
|---|---|
| `turn.status !== 'completed'` | 공급자가 준 `status`·`reason` 을 폐기하고 코드만 남김 |
| `this.child.stderr.resume()` | **stderr 통째로 폐기** — CLI 는 여기에 이유를 적는다 |

CLI 를 손으로 두드려서야 원인이 나왔다: `You've hit your usage limit.
try again at Aug 8th, 2026 12:39 PM`. `codex doctor` 는 16 ok · 0 fail 이고
로그인도 돼 있다 — 막힌 것은 할당량 하나다.

**수리**: 아는 조건만 코드로 분류한다(`USAGE_LIMIT`·`RATE_LIMIT`·
`NOT_LOGGED_IN`·`UNKNOWN_MODEL`). **원문은 싣지 않는다** — 실측된 usage-limit
메시지에도 결제 URL 이 들어 있다. 시험이 `chatgpt.com` 이 오류로 새지 않는지 지킨다.

> 이 세션 내내 **자가 부풀어 있는 것**을 고쳤는데 이것은 **반대 방향의 같은 병**이다.
> 실행 실패를 성능으로 기록하면 멀쩡한 모델을 못 쓴다고 판정하게 된다.
